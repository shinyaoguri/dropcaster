# Issue を実装可能にする

共通規約は [AGENTS.md](../../../AGENTS.md)。「起票」と「実装の委任」を分け、1 件ずつ調べる。

1. `gh issue view <番号> --json title,body,labels` で本文を読む。
   `git fetch origin main` で更新し、`git log -5 --oneline origin/main` と実際のコードを確認する。
   `gh issue list --state all --search '<キーワード>'` と、関連する merged PR で重複・解決済みを調べる。
2. 完了条件を「まだ有効」「既に満たされている」「差し替えが必要」に分ける。
   行番号・名前など事実のずれを直す。目的・仕様を変える必要があるなら、選択肢と推奨を示す。
3. 操作・入力 → 現在の結果 → 期待する結果 → 代償、の具体例を 1 つ以上書く。
   完了条件は「実装する方法」ではなく「観察できる結果」で書く。測定・再現は仮説と区別する。
   見た目・動きが関わるなら [visual-evidence](../visual-evidence/SKILL.md) に従う。
4. バグなら破られた仕様と、それを負う別の入口・呼び出し元を探す。
   `rg` の検索式と結果・未確認範囲、同じ原因の既存 Issue を残す。
   viewer は gallery / hosted、入力は pointer / keyboard、出力は inline / popup など、
   その仕様が適用される経路を調べる。すべてのバグに全組合せを機械的に課さない。
5. 既存の Issue 本文をローカルの一時ファイルで編集し、`gh issue edit <番号> --body-file <ファイル>`。
   書く直前に再取得し、他者の変更を上書きしない。変更した前提は経緯が分かるように記載する。
   長文は先頭に要約と人の判断事項、末尾にエージェント名を置く。
6. 他者が起票した Issue には自分で `verify: triaged` を付けず、メンテナへ調査結果を示す。
   自分で起票したものは、既存の合意で完了条件を確定できる場合に限り付けてよい。
   満たされた Issue は閉じる根拠を示す。棚卸しで結論が変わらなければ同じコメントを繰り返さない。

未トリアージの調査は実装せずに進めてよい。ready な Issue を選ぶコマンドとラベルの準備は
[エージェント環境](../../../docs/agent-environment.md) を参照する。
