# 0016: 開発規約と検証の記録をエージェント間で共有する

## 状態

採用 — 2026-11-13。ユーザーが mokume との比較後に導入案全体を採用した。
[導入 Issue #140](https://github.com/shinyaoguri/dropcaster/issues/140)。

## 文脈

記憶ゼロで再開できる記録規約は CLAUDE.md にあったが、Codex と人間の共通入口がなかった。
Issue テンプレートの「実装完了」「テスト追加」は期待する挙動を特定せず、PR のチェック欄だけでは
完了条件と検証の対応が分からなかった。一方、PR #98 / #100 には比較証跡・回帰確認・未確認範囲を
明示した良い実践があり、最新 CI には両 viewer エントリの描画・復旧・会場操作の検証が揃っている。

CI は PR の edited でも verify を再実行し、タイトル修正や本文の検証結果追記に全ビルドと
ブラウザテストを起動していた。これはテンプレート充実で増えるメタデータ編集にも影響する。

参照したのは [mokume の AGENTS.md](https://github.com/mokume-metal/mokume/blob/f9d4aa142001fdf50ea3c88e57cd33d7ea674082/AGENTS.md)、
同リポジトリのエージェント手順と PR テンプレート。dropcaster に合わせて独自に記述する。

## 決定

- 共通規約の正本を root AGENTS.md に置き、CLAUDE.md は参照、CONTRIBUTING.md は参加の入口、
  DEVELOPMENT.md は実行手順とする。規約を各文書へ複写しない。
- Issue は操作・変更前後の具体例と観察可能な完了条件、PR は条件ごとの検証結果・未確認範囲を持つ。
  実装で閉じる Issue の完了根拠は PR 本文に置く。
- トリアージ、独立した反証、視覚的な証跡の手順をリポジトリ内に置き、Claude / Codex から同じ正本を参照する。
  実装可能な Issue は verify: triaged、進行中は既存の status: in progress を使う。
  未トリアージの調査と実装の委任を分け、既存 Issue を一括で着手可能にしない。
- バグ修正では同じ根本原因が及ぶ範囲を探し、独立した担当者の反証と対応を残す。
  表示・動きは before/after と対象版・環境を記録し、未確認を検証済みにしない。
- PR タイトル検査を既存 CI から独立した pr-policy.yml に置き換える。ジョブ名は verify / pr-policy のまま、
  コード検証の全段を維持する。現在のタイトルを API から読み、既定ブランチの検査を実行する。
  編集イベントで verify を skipped にする方式は、重い run の打ち切りや未検証の成功扱いを招くため採らない。
  PR policy は短い read-only job とし、同時のイベント同士を concurrency で打ち切らない。
- 新しいゲート・hook・ラベル・ワークフローは実害の Issue を根拠にし、既存責務・native 機能・置換を先に比較する。
  今回は既存の CI の責務分割と native ラベル・検索・sub-issue を使い、形式だけを検査する新しいゲートは追加しない。

## 影響

どのエージェントでも同じ規約から開始でき、PR から完了根拠を確認できる。
独立した反証と証跡作成には手間がかかる。使えない環境では未実施を明記し、必要な確認を Draft で引き継ぐ。
規約の強制範囲は文書による運用で、ラベルや表の存在だけを保証する自動検査は設けない。

専用 GPU runner・日次リリース・Issue Type・大量の hook・自動マージの委任は移植しない。
これらは比較時に導入を推奨しなかった基盤・権限の変更で、今回の採用範囲に含めない。
既存の軽量 ADR・Conventional Commits・freshness・依存更新・ブラウザ検証は継続する。
PR の base 変更後は reopen / push により新しい base のコード検証を行う。
新 workflow の初回実行は PR で確かめ、必須チェック名は変更しない。
