# 0018: Gist は直接取得を基本とし、ホスト版の Worker 中継は予備にする

## 状態

採用 — 2026-11-14。メンテナが会話で、直接取得を基本の方針に戻し、Worker の中継を予備の経路にするよう指示した。
[#144](https://github.com/shinyaoguri/dropcaster/issues/144)。[ADR 0017](0017-hosted-gist-api-proxy.md) の
取得順 (中継を先に使う) を改める。中継そのものの仕組み (トークン・ETag・キャッシュ・失敗時の扱い) は 0017 のまま。

## 文脈

ADR 0017 で、ホスト版の viewer は Gist を `/gist-api` (Worker がトークン付きで GitHub に問い合わせる中継) から
先に取り、使えないときだけ `api.github.com` へ直接取得するようにした。本番での動作は確認済み
([#142 のコメント](https://github.com/shinyaoguri/dropcaster/issues/142#issuecomment-6870144587))。

中継を先に使うと、ホスト版の Gist の読み込みはすべて、1 つの共有トークンと Worker を通る。
トークンが失効したり乱用で枠が尽きたりすると全員に影響し、ふだんの経路がギャラリーと違うので、
挙動の違いも追いにくい。直接取得が困るのは、同じ IP から大人数が使って枠が枯れる場面 (授業・会場) に限られる。

## 決定

- viewer はまず `api.github.com` へ直接取得する (ギャラリーと同じ経路)。
- 直接取得の結果で次のように分ける。
  - 200 で JSON → それを使う。中継は呼ばない。
  - 404 → 「Gist が無い」で確定する。中継に聞いても答えは同じなので、トークンの枠を使わない。
  - 中身が扱えない (`GistFormatError`) → そのまま確定する。
  - 制限 (403 + remaining 0 / 429)・その他の 4xx/5xx・通信失敗・JSON でない応答 → `gistApiBaseUrl` があれば中継を試す。
- 中継の 200 は使う。中継の印 (`x-dc-gist-proxy`) が付いた 404 は「Gist が無い」で確定する。
  それ以外で中継も使えなければ、**直接取得のエラー**を投げる。制限なら `GistRateLimitError` の待ち時間の案内は従来どおり。
- 設定名と値 (`gistApiBaseUrl: '/gist-api'`)、Worker・中継・Service Worker の実装は変えない。

## 退けた案

- **中継を先に使う (ADR 0017 のまま)**: 枠の消費が最も少なく、授業でも追加の往復が無い。ただし、ふだんの読み込みが
  すべて共有トークンと Worker に依存し、トークンの失効や乱用が全員に及ぶ。
- **直接取得の失敗をリセット時刻まで覚えて、その間は中継へ直行する**: 枯れた後の 1 往復を省ける。ただし
  `/gist/<id>` を開くたびにページが読み直されてメモリの状態は消えるので、効く場面が少ない。
  必要になったら (例: 同じページで何度も読み直す使い方が出たら) 足す。

## 影響

- 授業では、1 時間に最初の約 60 回は教室の IP の枠を使う。枯れた後の読み込みは、直接取得の制限応答を
  1 往復はさんでから中継へ進む。制限中の応答は枠をさらに消費しない。
- 中継の枠 (5000 req/時) を使うのは、直接取得が使えないときだけになる。
- 直接取得が通信失敗のとき、Service Worker の NetworkFirst が手元の版を返すことがある (オフライン用の従来の挙動)。
  その場合は応答が返ったとみなされ、中継へは進まない。
- トークン未設定・失効の Worker では、枠が枯れた利用者に直接取得の制限エラーが出る (中継が無い場合と同じ)。
