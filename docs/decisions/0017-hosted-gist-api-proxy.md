# 0017: ホスト版は Gist API を Worker がトークン付きで中継する

## 状態

採用 — 2026-11-14。メンテナが会話で案 D (Worker による中継) を選び、PoC で動くことを確かめてから実装した。
[#142](https://github.com/shinyaoguri/dropcaster/issues/142)。[ADR 0006](0006-gist-as-second-sketch-source.md)
の「認証は付けない」をホスト版について改める。

## 文脈

ADR 0006 では、Gist を viewer から GitHub API へ認証なしで直接取得すると決めた。未認証の枠は
「60 req/時・IP 単位」で、そこでは「共有回線のイベント会場では枯渇しうる。恒常的に足りなくなったら
認証トークンを足す。ただしホスト版でトークンを配ると誰でも使えてしまう点は別途考える」としていた。

大学の演習授業では、数十人が同じネットワーク (外から見て同じ IP) から使う。40 人がそれぞれ
1 時間に 6 回、canvastage で直して開き直すと 240 回になり、枠の 4 倍になる。Service Worker の
キャッシュはブラウザごとなので、学生どうしで共有されない。

実測 (#142 のコメント、2026-11-14):

- 認証なしでは、ETag を付けた条件付きリクエストの 304 でも枠を消費する。
- 認証付きでは、304 は枠を消費しない (`X-Ratelimit-Remaining` が変わらない)。
- PoC: `wrangler dev` 上の Worker でトークン付きで中継した。更新の無い再取得は 304 で枠を消費せず、
  Gist を更新すると約 6 秒で新しい版が返った。

## 決定

- ホスト版の Worker に `/gist-api/gists/<id>` を足す。Worker は secret の `GITHUB_TOKEN` で
  `GET https://api.github.com/gists/<id>` を呼ぶ。中継するのは 20〜64 桁の hex の ID と、
  GET / HEAD だけ。任意の API の踏み台にはしない。
- 鮮度は ETag で確かめる。
  - Worker は `caches.default` に、前回の本文・ETag・取得時刻を持つ。
  - 取得から 5 秒以内の再要求は、問い合わせずに返す (同時アクセスをまとめる)。
  - それ以降は `If-None-Match` で確かめ直す。
  - 304 ならキャッシュを返し、200 なら置き換え、404 なら消す。
  - 制限・障害のときは、手元に版があれば `x-dc-stale: 1` を付けて返す。
- ブラウザへの応答は `Cache-Control: no-cache` にする。鮮度は Worker が判断し、ブラウザ側では
  Service Worker の NetworkFirst (GIST_CACHE) だけを通す。
- トークンには権限を何も付けない (fine-grained PAT。公開リポジトリは読み取りのみ)。
  漏れても読めるのは公開情報だけになる。トークンは利用者に配らない。
- viewer は設定 `gistApiBaseUrl` があればその中継を優先する。未設定・503・制限・5xx・通信失敗のときは、
  `api.github.com` への直接取得 (従来の経路) に切り替える。中継の 404 は「Gist が無い」として確定する。
  - ホスト版は `'/gist-api'` を設定する。
  - ギャラリーは既定で未設定のまま。必要なら自分で中継を置いて設定できる。
- トークン未設定の Worker は 503 を返す。Cloudflare の共有 IP から認証なしで呼ぶと、他の利用者と
  枠を分け合ってすぐ枯れるため。secret を登録する前にデプロイしても、挙動は従来と同じになる。

## 退けた案

- **制限中は Service Worker がキャッシュを返す (A)**: キャッシュはブラウザごとで、中身はその人が
  前に開いた版。授業では「直したのに反映されない」に見え、エラーより原因が分かりにくい。
- **raw URL (`gist.githubusercontent.com`) で取得する (B)**: API の枠の外だが、所有者名が必須
  (所有者を省くと 404)。所有者名を経路とプロジェクトファイルに持たせる必要があり、保存形式が変わる。
  ID だけの入力には効かない。CDN のキャッシュ (max-age=300) もある。
- **利用者が自分のトークンを入れる (C)**: 作品のコードは同一オリジン・sandbox なしの iframe で動く
  ([ADR 0001](0001-same-origin-sandboxless-iframe.md))。他人の Gist に書かれたコードから、保存した
  トークンを読めてしまう。
- **Worker がトークン無しで中継する**: Cloudflare の送信元 IP は多数のテナントで共有されるので、
  未認証の枠はかえって当てにならない。

## 影響

- ホスト版の利用者全体で、1 つのトークンの枠 (5000 req/時) を分け合う。枠を使うのは Gist の中身が
  変わったときだけなので、授業規模 (1 クラスで 1 時間 240 回の見積もり) なら約 20 クラス分に収まる。
- 乱用されると枠を使い切る可能性がある。そのときは利用者側が直接取得 (各自の IP の枠) に戻るだけで、
  サービスは止まらない。問題が出たら、Cloudflare のレート制限ルールなどで絞る。
- トークンの発行・登録・更新はメンテナが行う (手順は DEVELOPMENT.md)。トークンの名義は運用で決める。
- OpenProcessing API も同じ問題を抱える (全リクエストにトークンが必要・毎分 40 回、認証なしではすぐ 429)。
  ただし、1 つのトークンで他人のリクエストを中継してよいかが規約上はっきりしない。応答も `no-store` で
  ETag が無い。そのため、この ADR では扱わず、#142 で規約の確認を待つ。
